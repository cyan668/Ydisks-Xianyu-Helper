## 数量策略契约

在自动化规则的每条“卡密库存/发货模板”内容上选择：

- **按购买数量**（`per_item`）：实际取卡份数 = 购买件数 × 配置份数。字段省略时保持此历史行为。
- **每单固定份数**（`per_order`）：实际取卡份数 = 配置份数，不乘购买件数。

策略存入该动作 `config_json.quantity_mode`，随运行 `ActionPlan` 冻结，无数据库迁移。
模板动作的策略作用于各变量绑定的 `delivery_count`，不再叠乘模板动作外层份数；模板凭证仍以实际消息条数计量。
未知策略在保存及匹配动作执行时拒绝；历史补发按原计划计算，不读取现行规则替换历史义务。
列表中的坏配置按动作显示告警，不阻断其它规则；未知策略必须明确重选，损坏 JSON 不会被静默覆盖。
不放宽付款事实、金额、购买数量、SKU、幂等、未知结果或库存恢复门禁；不新增 MTOP 请求。

商品模板库/批量发布原入口仍按既有默认生成规则；需要固定份数时，在生成后的自动化规则页设置。
它们与已有规则编辑不是同一对象，不能借本次改动自动重写既有模板或线上规则。

## 黑名单保护契约

交易黑名单按当前用户隔离，支持用户全部账号、单个账号、单个账号的指定商品；只按稳定买家 ID 匹配，兼容 `@goofish` 后缀，不按昵称猜测。商品级优先于账号级，再到用户级；停用条目不参与匹配。新建默认停用，关单另有独立开关。它不代替平台会话拉黑，也不自动关闭普通关键词/AI 客服回复。

自动发货、赠品、模板、API 卡取卡、逐份库存、快照补发、人工完整发货和“仅确认发货”均核验实时黑名单；查询失败或相关规则存在但身份缺失时停止。没有配置黑名单的旧调用保留原订单事实合同。

仅经过既有卖家核验、账号启用和暂停门禁的 WS 拍下/付款系统事件，才允许尝试自动关单；调度恢复和人工补发只拦截，不发起关单。关单还要求本地同账号订单身份一致且仍为待付款/待发货，已有运行、发送内容或不确定结果时不提交。保持原砍价免拼与付款发卡阶段顺序，不改变冻结验证码或认证恢复。

每个账号/订单请求前持久化唯一占用，最多一次 MTOP 请求，沿用统一账号级节流；不新增扫描、并发、Token 刷新或自动重试。明确成功后原子收口本地关闭状态；超时、错误响应或保存失败保留阻断并发送独立人工处理通知。重复事件、重启、删除或停用规则都不能解除未知关单结果保护；需要在平台人工核对并处理该交易，不自动继续发货。

协议事实来自源项目固定快照的 [个人黑名单匹配](https://github.com/zhinianboke/xianyu-auto-reply/blob/a58dea0d8ef43d4f467f09b5607af4821710700a/websocket/app/services/xianyu/delivery_rules/personal_blacklist_rule.py#L90-L167) 与 [Cookie 卖家关单实现](https://github.com/zhinianboke/xianyu-auto-reply/blob/a58dea0d8ef43d4f467f09b5607af4821710700a/websocket/app/services/xianyu/auto_delivery_handler.py#L3674-L3808)。不使用需要 ISV accessToken 的另一套关单接口，也不复制源项目连续重试策略。

新增三方言迁移 `00059_buyer_blocks`，数据只含配置和关单占用。代码按叠加 PR 开发，基于数量策略分支；两项分别审核，数量策略接受后再把黑名单 PR 基线转为 `codex/custom`。本轮没有导入真实黑名单或调用真实订单关单接口；线上部署和账号仍保持原状态。
